实现要点（落地到真实 Obsidian canvas 时怎么办）


    
1. 数据存哪：三个方案对比

    
约束：canvas 的 text 节点 JSON 只有 {id,type,text,x,y,width,height}，没有独立的补充描述字段。因此补充描述要么塞进 text，要么存在 canvas 之外。

    

      
方案做法优点缺点 / 代价

      

        A 分隔符内联
        text = 原文 + "\n\n---\n\n" + 补充描述
        单字段自包含；Obsidian 全文搜索能搜到补充描述；导出/复制卡片不丢。
        需要解析；用户手改正文极易破坏分隔符（--- 也是 markdown 分割线，语义撞车）；卡片进入编辑模式会看到原始标记。
      

      

        B HTML 注释包裹 ★
        text = 原文 + "\n<!-- ppd-note-start -->\n" + 补充描述 + "\n<!-- ppd-note-end -->"
        仍是单字段自包含、可搜索；阅读模式/预览下 HTML 注释不渲染，卡片看起来干净；起止标记成对出现，解析可靠、易做容错（缺闭合标记就吃到结尾）；与 markdown 语法零冲突。
        双击进卡片编辑模式能看到注释源码；删除卡片时标记一起走（这反而是优点）；需要同时维护一个极小的 sidecar 存「折叠状态」（见第 4 点）。
      

      

        C 插件 data.json sidecar
        canvas 的 text 完全不动，补充描述按 node.id 存进 .obsidian/plugins/pdf-plus-drag/data.json
        零污染 canvas、不干扰用户手改正文、不会被 --- 之类的正文内容误伤。
        卡片不自包含：复制卡片/导出 canvas/分享给别人，补充描述全丢；node.id 在 duplicate 时会变，映射断裂；data.json 通常不在同步范围或同步时机不一致，多设备会错位；搜索不到。
      

    

    
推荐方案 B，理由：摘录卡片的核心价值是「原文 + 我的想法」绑定在一起，自包含是刚需；而 B 同时拿到了自包含、可搜索、解析可靠三个好处，代价只有「编辑模式能看到注释源码」这一条，可以通过命令「编辑补充描述」（弹 Modal 输入）绕开，让用户几乎不用直接碰源码。

    代价与兜底：① 解析器必须同时兼容 A 的 --- 分隔符，便于将来从 A 迁移；② 必须容错（缺闭合标记、标记重复、标记出现在原文里）→ 优先取最后一对标记，缺闭合就吃到结尾，并把异常写日志不抛错；③ 折叠状态这类纯 UI 态不进 text，存 data.json 即可（内容自包含 + UI 态外置，是 B 与 C 的折中）。


    
2. 卡片高度怎么算

    
沿用插件已有的 estimateSizeFor 思路：离屏 span 测宽 → 算换行行数 → 行高 × 行数 + padding，再叠加补充描述区的高度。

    
    
      
  • 离屏测宽：建一个 position:fixed;left:-9999px;white-space:pre;visibility:hidden 的 span，用和卡片渲染完全相同的 font-size / font-family，逐行 getBoundingClientRect().width；
    • 
      
  • 行数：lines += Math.max(1, Math.ceil(measuredW / innerW))，innerW = width - padX - 左边框/缩进；
    • 
      
  • 总高：h = padY + 原文行高×原文行数 + 间距 + 补充描述区高，补充描述区高 = noteLineH × noteLines + notePadY + 头部行高；折叠时退化为一个 chip 的固定高（约 26px）；
    • 
      
  • 宽度策略：width 只由原文决定（补充描述不撑宽卡片，否则一动整张卡就晃），只让高度自适应；
    • 
      
  • 图片卡（![[]]）同理：图片等比高 + 回跳行 + 补充描述区高；
    • 
      
  • 幂等保护：抄 fitNode 的做法——对 text 取 simpleHash 存起来，hash 未变就不重算（用户手动调过高度不被反复覆盖），只有 size 变化超过 2px 才真正写回。
    • 
    

    
演示里工具栏右侧读数同时给出估算值（离屏测宽那套）和实测值（真实 DOM 高度，作为验收基准），两者应当接近。


    
3. 与「摘录文档同步」的冲突（重点）

    
现状：main.js 的 canvas→md 同步，是把 node.text 去掉 ^ex-xxxx 那一行后整段作为条目正文写进 <PDF名>-摘录.md。如果补充描述混进了 text，摘录文档一定会被污染——你的私人想法会被当成原文一起写进摘录文档，还会跟着条目的嵌套引用一起出现在大纲里。

    
处理：在同步链路的入口处先做一次剥离，插件里现在的 body 提取处（node.text.split("\n").filter(l => !/^\s*\^ex-…$/)）改成：

    
    
      
  • const { quote } = splitNote(node.text); 先切掉补充描述段；
    • 
      
  • 再对 quote 做原有的「去 ^ex 行 + trim」；
    • 
      
  • 关闭「剥离」开关时预览面板会标红，就是未剥离时摘录文档被污染的样子（工具栏那个复选框可来回切）。
    • 
    

    
另有两个连带问题：① 反方向（md → canvas）目前是整文件重写、单向覆盖，补充描述绝不能参与反向同步，否则会被 md 覆盖丢失；② 摘录 md 里要不要输出补充描述是产品选择——建议默认不输出，另开一个开关「摘录文档也带补充描述」，带上时用 > [!note] callout 或缩进块区分，避免和原文混淆。


    
4. 折叠状态与编辑状态的存放

    
    
      
  • 折叠/展开是纯 UI 态，不能写进 text（会污染内容与 hash），存 data.json：notes[node.id] = {collapsed:true}；
    • 
      
  • 编辑入口两条：卡片上直接编辑（contenteditable / 劫持 canvas 的编辑态），或命令「编辑补充描述」弹 Modal——后者更稳，不依赖 canvas 内部 DOM；
    • 
      
  • 写回 canvas 要用插件既有的 selfWritten 标志防回环：插件自己写的 canvas 文件变更不能再触发一次同步；
    • 
      
  • 输入防抖（建议 600~800ms）后再重写 canvas 文件，避免每敲一个字就整文件 IO。
    • 
    


    
5. 落地清单（最小实现）

    
    
      
  • 纯函数 splitNote(text) / composeNote(quote, note) / stripNoteForExcerpt(text) → 可单测，放在 ppdDiffCanvasNodes 那批导出函数旁边；
    • 
      
  • 渲染：canvas 是 Obsidian 自绘的，插件改不了节点内部 DOM，所以「绿框」效果只能靠 markdown 本身表达（callout > [!ppd-note] 或引用块 + 高亮 ==…==），本演示的绿框对应真实环境里的 callout 渲染结果；
    • 
      
  • 命令：添加/编辑补充描述、切换折叠、清除补充描述、批量展开/折叠；
    • 
      
  • 旧卡兼容：splitNote 找不到标记时返回 note=""，老卡片零改动照常工作；
    • 
      
  • 迁移：若日后从 A 换到 B，写一次性命令扫描所有 canvas 重写 text；反向解析保持兼容即可平滑过渡。
